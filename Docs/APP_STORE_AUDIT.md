# App Store Compatibility Audit

This audit covers the current Ahoge architecture. It does not assert that App Review will approve Ahoge; technical code-loading compliance and third-party-content review risk are separate questions.

## Current remote source model

Ahoge ships native source runtime code in the application binary under `Ahoge/Data/Sources/`. The remote source importer accepts JSON repository/package/source objects and converts them into `SourceDescriptor` / `ImportedSourceDescriptor` values. Runtime selection ultimately maps those descriptors to native `SourceEngineFamily` implementations already compiled into Ahoge.

The current importer does **not** download and execute JavaScript, Swift, native libraries, scripts, bytecode, or another general-purpose interpreted program from a source repository.

That distinction should be preserved. Remote definitions can change configuration for an existing native runtime, but they should not become a mechanism for shipping new executable application behavior after review.

## Field classification

The current `SourceRepoImporter` accepts or derives the following remote fields.

| Field / concept | Classification | Notes |
| --- | --- | --- |
| package `name` | content metadata | Display/package metadata. |
| package `pkg` | content metadata / identity | Package identifier used for repository identity and legacy classification heuristics. |
| package/source `lang` | content metadata / configuration | Selects language metadata. |
| package/source `version` | content metadata | Definition version. |
| package/source `nsfw` | content metadata / configuration | Adult-content flag used by Ahoge UI policy. |
| source `id` | content metadata / identity | Stable source identity. |
| source `name` | content metadata | Display name. |
| source `baseUrl` | configuration/data | Network endpoint consumed by a compiled native runtime. |
| source `rateLimit` | configuration/data | Request-policy configuration. |
| source `overrides` | selectors/rules | Declarative key/value behavior knobs understood by compiled native code. These must remain a closed, documented set rather than becoming a scripting language. |
| `mangaSubPath`, `dateFormat`, `hasProjectPage`, `chapterListPageOverride` override examples | selectors/rules | Declarative parsing/routing configuration interpreted by fixed Swift code. |
| source `engine` / `family` | native runtime reference | Selects an `SourceEngineFamily` already compiled into Ahoge. It does not download an engine. |
| source `adapter` | native runtime reference / selector | Selects a fixed adapter implemented in the app, such as `mangabox`, `ezmanhwa`, or `heancms`. Do not let this become an arbitrary executable module name loaded from the network. |
| source `apiUrl` / `apiURL` | configuration/data | API endpoint for a supported native adapter. |
| package `apk` | content metadata only in the iOS app | The importer normalizes and stores the URL for compatibility with extension-repository formats. Ahoge does not install or execute the APK. This field is unnecessary for iOS execution and may be worth omitting from Ahoge-native manifests to reduce App Review ambiguity. |
| `capabilities`, feature flags, filter/preference schema generated by Ahoge | selectors/rules / UI metadata | Produced by native code from known families/configuration. |

### Executable/interpreted code

Current classification: **none found in the imported source-definition format**.

The importer uses `JSONSerialization` to read structured data. It does not evaluate remote text as JavaScript, shell commands, Swift, WebAssembly, Lua, Python, or another language. The current native runtime availability check recognizes a fixed set of compiled families/adapters.

If a future source format adds JavaScript snippets, CSS/DOM scripts executed in a web view, expression languages with general computation, downloaded frameworks/dylibs, executable bytecode, or remotely supplied code that materially changes application functionality, this audit must be reopened before shipping that format.

## Important boundary: selectors and parsing rules

Declarative selectors/rules are safer than remote executable code, but the boundary matters.

A rule like:

```text
mangaSubPath = "series"
```

configures a path consumed by compiled Swift code. A hypothetical rule like:

```text
evaluate = "function(response) { ... }"
```

would cross into remotely supplied executable/interpreted behavior and should not be added casually.

The problem is not remote data. The problem is turning remote data into a general code-loading mechanism.

## Runtime architecture recommendation

Keep the existing model:

1. Native runtime engines ship inside Ahoge.
2. Remote repositories provide source identity, endpoints, metadata, fixed selectors/rules, and references to those native runtimes.
3. Unsupported engine families remain unsupported/planned until native support is added in a new Ahoge binary release.
4. Updating a definition for an existing runtime does not require a binary release.

This keeps source maintenance fast without letting the remote repository introduce arbitrary executable application functionality.

## App Review risks separate from code loading

Even if the remote-source architecture remains declarative, Ahoge has significant review considerations because it accesses third-party manga/content services. These should be assessed separately from the executable-code rule:

- whether the app facilitates access to copyrighted material without authorization;
- whether listed sources violate third-party site terms or access controls;
- whether adult-content sources and filtering satisfy App Store requirements;
- whether source installation lets users reach content/features Apple would consider outside the reviewed experience;
- whether scraping behavior, anti-bot workarounds, cookies, or authentication handling raise privacy/security concerns;
- whether the app accurately represents its relationship (or lack of relationship) with third-party services.

Passing the remote-code audit does not resolve those content/service issues.

## Distribution-specific behavior

Ahoge's new `DistributionChannel` abstraction has three channels: `development`, `sideload`, and `appStore`. App Store/TestFlight builds must use `appStore` so the app does not direct reviewed users toward SideStore or an unsigned IPA.

No signing credentials belong in source control. Future App Store Connect credentials must be supplied through encrypted CI secrets.

## Persistence / upgrade risk

The production bundle identifier remains `com.quackyprog.ahoge`. Keeping that identity is necessary for normal in-place upgrades to retain the application's container.

Current persistence has useful compatibility behavior:

- `PersistedState` has an explicit `schemaVersion` and decodes missing fields with defaults.
- `DatabaseSnapshot` decodes missing collections safely and contains a legacy `cachedChapters` -> `downloadedChapters` migration path.
- database/import/download files are under the app's Application Support container.

However, `AppStateStore.migrate` currently only changes `schemaVersion`; it is not a version-by-version migration engine. A future change that renames fields, changes value shapes, or removes enum cases can still make older data fail to decode. Before a production release changes persisted models, add fixture-based tests that load snapshots from the previous shipped schema and verify library, progress, downloads, source repository records, and preferences survive.

## Audit result

The current architecture is compatible with the preferred technical direction for App Store review: fixed native engines in the binary plus declarative remote source configuration. No remote executable/interpreted code was identified in the current source importer.

The main unresolved App Store risk is not the current JSON configuration mechanism. It is the policy/content relationship with third-party manga services and any future temptation to make remote definitions powerful enough to behave like executable extensions.
